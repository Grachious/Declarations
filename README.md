# Ранжирование регулирующих НПА для таможенных деклараций

Для каждой из 151 декларации (`data/declarations.jsonl`) возвращает top-10 наиболее
релевантных НПА из справочника 562 регуляций (`data/regulations.jsonl`), отсортированных
по убыванию релевантности, в файл `out/predictions.csv`.

## Установка

```bash
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt
```
Версии зафиксированы в `requirements.txt`. Python 3.10+.

## (Опционально) Скачать модель эмбеддингов

```bash
pip install sentence-transformers
python download_model.py
```

Скрипт сохраняет `intfloat/multilingual-e5-base` (~278M) в `./models/embedder`. 
Это единственное место, где решение обращается к сети, поэтому вынесено из `run.py` 
в отдельный скрипт.

## Запуск

```bash
python run.py --out ./out
```

На входных 151×562 парах занимает несколько секунд в чисто лексическом режиме и около
7 минут с локально скачанной моделью эмбеддингов на CPU. Сетевых обращений во время `run.py`
нет: наличие модели проверяется по локальному пути `models/embedder`, при её
отсутствии решение автоматически переключается на чисто лексический режим.

Результат: `out/predictions.csv`, столбцы `declaration_id, rank, regulation_id, score`.

## Подход

Данные из `regulations.jsonl` - это по сути список контролирующих пунктов. 
Каждый пункт описывает категорию товара через технические признаки. 
У деклараций нет размеченной регуляции, поэтому это
задача unsupervised text retrieval.

Реализован гибридный ранжировщик из трёх сигналов, комбинируемых взвешенной
суммой после построчной min-max нормализации:

1. **BM25** (реализация с нуля в `src/bm25.py`, без стороннего пакета) - классический
   сильный бейзлайн для короткого запроса против корпуса документов, устойчив к разной
   длине текстов, хорошо ловит точные термины.
2. **TF-IDF + косинусное сходство** (sklearn) на общем словаре деклараций и регуляций 
   более плавный сигнал, менее чувствительный к редким выбросам частоты термина, чем
   BM25; служит стабилизирующей добавкой.
3. **(опционально) Семантические эмбеддинги** (`intfloat/multilingual-e5-base`,
   косинусное сходство) - компенсируют случаи, когда декларация и текст НПА описывают
   одно и то же разными словами, где чисто лексическое совпадение слабое.

Веса по умолчанию: `w_bm25=0.5, w_tfidf=0.2, w_embed=0.3` (при отсутствии модели
эмбеддингов веса BM25/TF-IDF становятся 0.71/0.29).
Веса настраиваются флагами `--w-bm25 --w-tfidf --w-embed`; отдельного размеченного
валидационного набора для их подбора не было, поэтому веса заданы в связи с природой текста.

Русский текст нормализуется в `src/text_norm.py`: токенизация, лемматизация через `pymorphy2`,
иначе собственный лёгкий суффиксный стеммер. Короткий стоп-лист служебных слов вырезается.

## Рассмотренные альтернативы

- **Только TF-IDF/BM25 без лемматизации.** Проще и быстрее, но русская морфология 
  сильно увеличивает разреженность и теряет совпадения. Отклонено в пользу
  лемматизации/стемминга.
- **Только LLM-классификация (генеративная модель, промпт "выбери 10 НПА из
  списка").** Требует уместить 562 текста НПА в контекст на каждый из 151 запросов, 
  сильно медленнее, недетерминированно без фиксации seed/температуры. 
  Отклонено в пользу связки ранжирования.
- **Cross-encoder / LLM как re-ranker поверх top-N кандидатов от BM25.** Более
  качественный, но заметно более медленный вариант. Оставлен как возможное расширение, 
  не включён в базовое решение ради надёжного укладывания во временной лимит на CPU.
- **Использование `tnved_knowledge.txt`**. Проверено: ни один из 562
  текстов НПА не содержит явных кодов ТН ВЭД, то есть прямого моста "код → регуляция" в данных нет. 
  Сопоставление декларации с деревом добавило бы отдельный, шумный этап классификации,
  избыточное усложнение.
- **Единая нормализация без числовых токенов**.
  Отклонено: в этих текстах именно числовые пороги и есть смыслоразличающий признак 
  между похожими пунктами НПА, поэтому числа сохранены как токены.

## Сложности

- Нельзя количественно оценить качество итогового ранжирования на этих данных,
  только косвенно, через ручную проверку правдоподобия топ-совпадений.
- Внутри 562 НПА совершенно разные домены. Общий TF-IDF-словарь помогает
  модели не путать домены за счёт высокого IDF узких терминов, но
  требует, чтобы описание товара в декларации было достаточно специфичным.
- Многие пункты НПА отличаются друг от друга только числом,
  токенизация специально сохраняет числа как отдельные токены, а стеммер их не трогает, 
  иначе такие пункты стали бы неотличимы по тексту.
- Смешанный русско-английский текст в декларациях — токенизатор оставляет латиницу как есть, 
  что корректно для собственных имён/моделей, но означает, что совпадение по бренду/модели напрямую
  между декларацией и НПА маловероятно.
- `G31_1` иногда описывает целый комплект, из-за чего релевантные термины
  размываются по всему тексту вместе с нерелевантными. BM25
  здесь работает лучше плотного эмбеддинга одной декларации целиком, так как отдельные
  совпавшие термины дают локальный вклад в счёт независимо от остального шума в тексте.

## Структура проекта

```
run.py                  # точка входа: python run.py --out ./out
download_model.py       # опционально, один раз, с интернетом
requirements.txt
src/
  text_norm.py           # токенизация, лемматизация/стемминг, стоп-слова
  bm25.py                 # своя реализация Okapi BM25 (без внешних пакетов)
  embeddings.py            # опциональный семантический сигнал (sentence-transformers)
data/
  declarations.jsonl      # копия входных данных
  regulations.jsonl
models/
  embedder/                # (создаётся download_model.py, отсутствует по умолчанию)
out/
  predictions.csv          # результат запуска
```
